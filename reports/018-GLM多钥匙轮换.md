## 背景
017 的存量精抽在 1,749 条处因单把 GLM coding 钥匙周配额耗尽（HTTP 429 / code 1310）停在断点。领导有多把智谱钥匙可用，要求：多钥匙轮着用，全部失效才轮到 DeepSeek。

## 做了什么
- `config.zhipu_api_keys()`：收集 `ZHIPU_API_KEY`（总开关，必填）+ `ZHIPU_API_KEY_2`…`_9`（备用，可空），空槽自动跳过；惰性读取可被测试 monkeypatch。
- `GLMExtractor` 接受钥匙列表：**额度尽（429/1310，兼容两种错误体形态）或钥匙无效（401）→ 当场热切换下一把并重试同一请求**；普通 429（限流非 1310）只退避不烧备用钥匙；全部钥匙死亡 → 抛 `RateLimited` 落在断点（绝不静默降级）。线程安全（锁 + 失败索引比对，避免并发双切）；旧 httpx client 弃用不关闭（在途请求安全），泄漏上界 = 钥匙数。
- `auto` 链顺序不变：GLM（多钥匙）→ DeepSeek → heuristic —— 即领导要的「GLM 全尽才用 DeepSeek」。
- 单字符串构造保持兼容（既有调用点与测试不受影响）。
- `.env` 已追加 3 个空备用槽位（保留原有钥匙，值全程未显示）。

## 使用
领导把新钥匙贴进 `.env` 的 `ZHIPU_API_KEY_2=`（及 _3、_4）等号后即可，其余零配置。默认模型仍为选型胜出的 glm-5.3-flash。

## 补充（同日第二轮）：每把钥匙可配独立模型与端点

领导的备用钥匙来自不同资源包（coding 套餐 / 按 token 计费包），各自只覆盖特定模型与端点——钥匙**不可互换**。故升级：
- `config.ZhipuKey(key, base_url, model)`；每个槽位可配 `ZHIPU_API_KEY_N_MODEL` / `ZHIPU_API_KEY_N_BASE_URL`，缺省回落全局值。
- 轮换时连端点与模型一起切，**重试请求自动改用新钥匙的模型名**（payload 在 _call 前构建，不改会拿旧模型打新钥匙）。
- CLI 显式指定模型只覆盖主钥匙；编号槽位保持各自资源包能用的模型。
- 测试 201 passed（+3：端点模型随钥匙切换 / 槽位伴随配置 / 覆盖只及主钥匙）。
