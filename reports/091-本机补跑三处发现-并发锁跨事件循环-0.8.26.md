## 二、产品缺陷：抓取并发锁跨事件循环（0.8.26 修）

- 现象：`ohp ingest --seed -c <香港 15 家>` 崩溃，`RuntimeError: Semaphore ... is bound to a different event loop`。15 家已登记、岗位 0 条。
- 原因：Moka、北森、理想三个适配器各有一个模块级的 `asyncio.Semaphore` 作礼貌限速。asyncio 的锁第一次有人排队时绑定当时的事件循环；`ingest --seed` 先用一个 `asyncio.run()` 校验种子、再用另一个抓取，三家 Moka 雇主在第一个循环里争两个名额，锁绑到了第一个循环，第二个循环一排队就报错。
- 修法：`ats/base.py` 新增 `PerLoopSemaphore`，每个运行中的事件循环各有一把锁（按循环弱引用存，MCP 工具在工作线程里各跑各的循环，创建时加线程锁）。三个适配器改用它，限速语义不变。
- 证据：用 0.8.25 的写法复现了原错误（三家 Moka、两次抓取，第二次报同样的 RuntimeError）；新测试 6 条：普通锁跨循环必报错（证明测试打得到）、新锁跨两个循环不报错、同一循环内仍限到 2 个并发、三个适配器都用新锁、全包扫描不许再出现模块级 asyncio 锁、三家 Moka 两次抓取端到端。
- 影响面：维护者命令 `ingest --seed` 必现；用户侧 MCP 长进程里只有同一次调用抓 3 家以上 Moka 或北森、且之前另一循环里排过队时才会撞上，概率低，一并发版。

## 三、Windows 上一条测试失败

`tests/test_hosted.py::test_bootstrap_reopens_the_index_after_installing` 在本机 Windows 上报 WinError 32。这条测试模拟的是「连接池里的读者在文件被删除替换后还读旧文件」，那是 POSIX 才有的情况；Windows 根本不让删除或替换别的连接开着的文件，替换会直接报错而不是读到旧数据。标为只在非 Windows 上跑，写明原因；CI 在 Linux 上照跑。
