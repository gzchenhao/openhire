# 071 · 领导定义的两头定位（求职雷达、雇主侧）对照现有能力与三条红线（2026-10-12，云端会话）

领导 2026-10-12 用一段话说清了 OpenHire 的两头：求职者侧是「求职雷达」，把猎头的个人功力放大给求职者，做四件事：企业雇主真伪辨别、平台潜力评估、职位监控与有效性评估、及时推送，第一时间把最有效的职位推给求职者的 AI agent（所以基于 MCP）；雇主侧是大型与中小型雇主发布与管理职位，最及时、精准地送达合适的求职者，类比最低成本的精准广告投放。本报告把这两头逐项对照现状，指出缺口和与三条红线的张力，列路线图，最后是两件要领导定的事。本报告不改代码，634 tests 不变。

## 一、求职者侧四项对照

| 愿景 | 现在有什么 | 缺什么 | 路线图 |
|---|---|---|---|
| 1. 真伪辨别 | `check_employer`：索引事实、RDAP 域名年龄、档案馆首抓、首页备案号、JD 红线词（含繁体与香港骗局特征）、OFAC 制裁名单本机比对、天眼查（求职者自己的 key）；香港与境外免费核验路径；每项带来源与时间，结尾写明「不是判断」 | 香港公司註冊處接口；联合国 / 欧盟 / 英国名单（OpenSanctions）；云端跑不了的项要本机跑 | 070 路线图第 2、4 条不变 |
| 2. 平台潜力评估 | `get_company_info`：在架数、中位在架天数、发布日来源、认领状态、`posting_dates_reported`；索引每周刷新 | 时间序列（在架数怎么变、新增岗位速度、关闭速度）；融资、并购、人事变动这类外部事实 | 从每周快照累积公司级时间序列，报「招聘速度」这类事实；外部事实只接有公开来源可引用的（行业资讯站的组织变化页是候选来源之一，先确认数据格式与许可）。**原则不变：给事实与出处，不给「潜力分」**，和 `check_employer` 一样 |
| 3. 职位监控与有效性评估 | `watch_intent` / `check_watches`（索引与招聘板都能盯）、`ghost_score`、在架天数、`relist_count`、`date_signal`、`read_board` 现读 | `read_board` 的岗位没有历史；relist 年龄下限 | 070 路线图第 5 条不变 |
| 4. 及时推送 | 没有。现在是拉：求职者的助手要调 `check_watches` 才知道有新岗 | 推 | `ohp watch-run`：本机定时命令（Windows 计划任务或 cron），有新匹配就本机通知（桌面通知或发到自己的邮箱），指纹与过滤条件都不出本机。MCP 协议没有「服务器主动找用户」的通道，这条路最稳也最省 |

结论：四项里三项有底座，缺的是第 2 项的时间序列和第 4 项的推。

## 二、雇主侧：愿景与红线的张力

现状：雇主进来只有两条路，认领（身份核实，不收钱）和自报岗位表（身份核实、`self_reported` 标记、90 天到期、不排序）；仓库里没有任何计费代码。

红线：第二条「排序绝不是付费参数」，第三条「雇主只为已授权、已交付的结果付费，绝不为曝光付费」。

「精准广告投放」这个类比和第三条正面冲突：广告的本质是雇主付钱换曝光。能走且不破红线的路：

1. **「精准」由求职者的 agent 完成。** 它拿着求职者自己的条件来搜、来盯、来打分（见第三节）。雇主不定向任何人；雇主侧要做的只是让岗位数据准确、及时、带真实发布日。
2. **雇主付费的唯一对象是「已授权、已交付的结果」。** `authorize_application` 已经存在，`applications` 表无个人信息：求职者的 agent 经本人授权把申请送到雇主自己的系统，雇主为这一次交付付费，不为被看到付费。这是按结果付费的直达投递，不是广告。
3. **排序、匹配度、推送顺序永远不因付费改变。** 大型雇主和中小型雇主在排序上一视同仁，这是第二条红线的要求。

## 三、从人岗匹配实践借来的规则（求职者侧匹配）

领导在猎头交付里用 AI 执行的人岗匹配有一套成熟规则：职能硬匹配（感知不等于 SLAM 不等于规控，方向不符直接排除）、八个维度（职能、行业、年限与量产、学历、薪酬、地点、年龄与应届、渠道）、10 分制、每条给「得分 / 失分」两行、规则由人定、AI 执行、人验收。

OpenHire 现在只有 `role_family` 与 `skills` 过滤加新鲜度排序，没有「求职者的条件对照岗位」的打分。可做一个只在求职者本机跑的 skill（暂名 `match-me`）：拿 `search_jobs` 或 `check_watches` 的结果对照本人简历，先判职能族再打分，每条给得分与失分。简历不经服务端，第一条红线无涉。进路线图，不动手。

## 四、要领导定的两件事

1. 雇主侧的对外说法：改成「按授权交付付费的直达投递」，不再用「广告」类比。
2. 大型雇主与中小型雇主是否完全一视同仁（我的建议：是，排序与展示都一样，差别只能在他们各自岗位数据的质量上）。

## 五、路线图（在 070 基础上更新）

1. 按官网找板。
2. 香港公司註冊處接口（本机验证）。
3. 装快照时保留用户态表。
4. 制裁名单扩到 OpenSanctions。
5. Workable / SmartRecruiters 适配器；relist 年龄下限；投递难度字段。
6. **新增：** 公司级时间序列（招聘速度事实）；`ohp watch-run` 本机推送；`match-me` 本机打分 skill；外部事实源的格式与许可确认。

## 六、领导裁定（2026-10-12 同日补记）

1. 第四节两件事都批了。「按授权交付付费的直达投递」太拗口，对外统一说**「按投递付费」**：投递指求职者本人授权、由他的 agent 送到雇主自己系统的那一次申请；曝光不收费，排序不收费。英文 pay per application。
2. 大型与中小型雇主排序与展示完全一视同仁。
3. 第二节候选的外部事实源（行业资讯站的组织变化页）经核现状不能接：没有公司字段、没有事件日期、标题经 LLM 改写、历史不足 90 天、信源许可没审过。已把结构化事件导出的口径给到对方；等导出存在且满 90 天、许可查清，再议是否接入，接入也只读公开 URL、只显示事件类型、日期、来源域名和链接。
