# 065 · 0.8.0：求职者一键企业背景查证 `check_employer`（2026-10-08 深夜）

领导：开工做 0.8.0；并问能不能把天眼查、爱企查这些也做进项目里做成一站式入口，不让求职者另装工具或打开别的链接；以后能不能做 token 批发中心。

## 一、做成了什么

新工具 `check_employer`（CLI `ohp check-company`），求职者问「这家公司是不是它说的那样」，助手返回一张**查证清单**：每一项只有五种状态（已查证 verified、未查到 not_verified、查不了 unavailable、不适用 not_applicable、待你补查 pending_user），每一项带来源和时间。没有总分，没有「安全 / 骗子」，结尾一句话写明「这是带出处的事实，不是判断」。

| 项 | 免费 / 付费 | 来源 | 一站式程度 |
|---|---|---|---|
| 在我们索引里：在架数、中位在架天数、发布日是雇主系统写的 / 雇主自报 / 我们首次抓到、是否认领；或「已知未收录 + 原因」；或「已停止运营」 | 免费 | 我们自己的索引与登记表 | 完全在工具内 |
| 域名注册日期 | 免费 | RDAP（注册局记录） | 完全在工具内 |
| 网站历史 | 免费 | 互联网档案馆首次抓取 | 完全在工具内 |
| 首页备案号 | 免费 | 公司官网首页一次 GET | 完全在工具内 |
| 岗位文本红线（境外高薪、包机票、不限经验、打字员……） | 免费 | 我们的特征词表 | 完全在工具内 |
| 工商登记（成立日期、经营状态、注册资本、参保人数、法定代表人） | 付费 | 天眼查 OpenAPI，**用求职者自己的 key**（`TIANYANCHA_API_KEY`，放在他自己机器上） | 设了 key 就完全在工具内；没设就标「待你补查」并给三条路：设 key、用助手已有的天眼查 MCP、免费手动（爱企查、公示系统） |

实测 `ohp check-company 理想`：索引 759 条在架（理想接口不给日期，如实标「首次抓到」）、域名 2000-11-29 注册、档案馆 2002-06-02 首次抓取、首页页脚「京ICP备19003172号」、工商登记待补查。全部一次 GET，不重试不换身份。

## 二、回答领导的两个问题

**一站式能不能做到？** 免费项已经完全在工具内。付费项（工商登记）也做进了工具：求职者在自己机器上设一个天眼查 key，工具就直接查，不用装第二个 MCP、不用开别的链接。做不到的只有一件：不能替他付钱。政府公示系统有验证码没有接口，天眼查按次收费，所以「有人付费」这一步绕不开；谁付，就决定了 key 在谁手里。今天的设计是求职者付、key 在求职者机器上、我们看不见 key 也看不见他查了谁。爱企查免费但没有接口，抓它等于破访问控制，按我们的规矩不做，所以它只能是手动链接。

**token 批发中心？** 技术上能做（我们买天眼查额度、求职者向我们买、我们的服务端代查），但有三道坎，我建议现在不碰，等有需求信号再议：
1. 天眼查的数据许可一般不允许转售或再分发，批发等于我们成了它的分销商，要先谈合作协议，否则违约；
2. 代查意味着求职者查了哪家公司、付了多少钱都经过我们的服务端，这是我们今天唯一没有的东西（现在连求职者查了谁我们都不知道）。「简历不出你的电脑」的信誉就建在这上面，一旦收钱代查，隐私承诺要重写；
3. 收钱本身要营业主体、发票、消费者保护流程，个人身份做不了。
如果将来要做，更稳的形态是「我们不经手钱和查询，只给一条推荐路径（天眼查的推广或合作链接）」。这条我没做，留给领导判断。

## 三、代码

- `src/openhire/verify/`：`checks.py`（纯检查与一次 GET 的网络检查，维护者脚本和求职者工具共用）、`tianyancha.py`（用用户自己 key 的最小客户端；接口形状按开放平台文档写，**还没拿真 key 跑过**，任何意外都报 unavailable 不编造）、`employer_check.py`（清单组装，默认函数运行时查找，测试可全替身）。
- `service.employer_check`：按搜索同样的规则解析公司名（歧义拒绝）；域名只在招聘页是雇主自己域名时自动取（Greenhouse / Moka 托管页不算），否则要求传 `domain`。
- MCP 工具 `check_employer`：只读、开放世界、幂等；说明里写死「不要加总、不要说安全或骗子」和隐私说明；阻塞的 HTTP 在工作线程里跑。
- CLI `ohp check-company <公司> [--domain] [--jd 文件] [--offline]`。
- `scripts/verify_employer.py` 改为复用包内检查（PASS / WARN / FAIL 评级给维护者）；`import_employer_roster.py` 的红线词表与邮箱域名检查也改为复用。
- 测试新增 `tests/test_employer_check.py` 12 项（解析与域名推导、已知未收录与已停运、红线词、带 key 与不带 key、天眼查信封处理、工具注册与说明、结果不含用户数据与 key）；验收测试的工具集合加 `check_employer`。
- README 加工具行与「这家雇主是不是它说的那样」一节；PRIVACY §3 加这个工具向谁发了什么（公司名或域名，从不发用户的任何信息）。

## 四、边界

- 清单只对索引里的公司和登记表里的公司保证「在不在我们这里」这一项完整；其他公司只给域名和网站那几项。
- 天眼查客户端没有真 key 实测。领导若有天眼查开放平台账号，给我一个 key 放 `.env`（不进仓库）我就能验一次；没有就等第一个用户反馈。
- 清单会把公司名或域名发给 RDAP、互联网档案馆、公司官网，天眼查只在用户设了 key 时才发；用户的任何信息都不发，结果不入索引不入快照。
