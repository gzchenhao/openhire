# 117 · 吸纳 career-ops 能力的建议（2026-10-30，云端会话）

## 背景

领导转来一份外部意见：把 career-ops 的核心能力并进 OpenHire，做成「求职者终端侧的 AI 个人求职 Command Center」。具体包括四项能力：岗位 A 到 H 反向评估与虚构岗位识别、按岗位定制简历、STAR 面试故事库、人脉与谈判话术。三种成本方案是：用户自备 key、借用用户现有的 AI 订阅、云端付费托管。请我给建议。

## 一句话

方向对，但一半已经做了。另一半要换个做法：**不在 OpenHire 里存简历、也不替用户算分**，而是做成一套随插件发布的「本机技能」。简历只留在用户自己的文件夹里，由用户自己的 AI 读；OpenHire 只给岗位事实。这样既能拿到 career-ops 那种「一套完整工作流」的体验和 star 吸引力，又不碰三条红线。

## 逐条看

**先纠正意见里的三个前提。**
* OpenHire 并没有已经被雇主采用的 `.well-known/jobs.json` 协议或「信任链」。我们的数据来自雇主自己的招聘系统接口；雇主自报岗位表只是一个小入口。对外不能这么说，说了就是夸大。
* 「方案二：借用户现有 AI 订阅、OpenHire 只提供数据和 Prompt 模板」正是 OpenHire 现在的架构：MCP 服务器加 8 个内置提示词，我们这边零 token 成本。这一块不用改。
* career-ops 并不只靠浏览器抓网页，它也读招聘系统接口（55 个以上数据源），而且有 `--verify` 在架复核。我们的差别在多周历史、公司招聘动向、查公司这三样，不在「结构化 vs 抓取」。

**四项能力：**

| 能力 | 建议 | 理由 |
|---|---|---|
| 岗位反向评估 | **做，但改成「匹配清单」，不打「低于 4 分不要投」的总分** | 匹配度（用户的简历对岗位要求）由用户的 AI 在本机算；岗位事实（在架天数、是否 30 天内还在、学历年限门槛、公司招聘动向）由 OpenHire 给。不给「虚构岗位」这种判决：在架时长是事实，不是假岗的证据。文案规矩第 4、5 条明确不许这么说，这一点不能为了体验破。`shortlist` 提示词已经是这条路子 |
| 按岗位定制简历 | **做成本机技能，不进服务器** | 读用户自己文件夹里的 `cv.md`，按岗位 `requirements` 和职位描述重排表述，只改写不编造；写出的文件留在本机。工具调用里永远只有 job_id。红线 1 只管服务器，本机文件不碰红线，但托管端点上绝对不做 |
| STAR 故事库 | **做成本机技能** | 同上，写进用户本机的 `stories.md`，OpenHire 不存、不看 |
| 人脉与谈判话术 | **只给模板，不自动发** | 起草不超过 300 字的打招呼信和谈判要点；发送由用户自己点。不碰任何平台的自动化 |

**三种成本方案：**

| 方案 | 建议 |
|---|---|
| 一、用户自备 key | 本机技能用不到：技能跑在用户自己的 Claude Code、Cursor、WorkBuddy 里，用的是它们的订阅。服务器端不需要 key |
| 二、借用户现有 AI 订阅 | **已经是现状**，继续 |
| 三、云端付费托管 | **现在不做**。收费需要营业主体、支付和 12 月的律师意见（「是否落入网络招聘服务」那一问还没答）；查公司页对 EarlyTip 承诺「永远免费无注册」；托管端点一旦生成简历，简历就要经过服务器，直接撞红线 1 |

## 具体做法（等领导点头）

1. 在仓库已有的 Claude Code 插件里加一个 `skills/` 目录：`openhire-job-search` 技能，四个模式，分别是 评估、定制简历、故事库、打招呼信。每个模式说明：
   * 读本机哪个文件；
   * 调 OpenHire 哪个工具（只传 job_id 或公司名）；
   * 写出哪个本机文件；
   * 简历内容不出现在任何工具参数里。
2. 同样四个模式也做成 MCP 提示词（第 9 到 12 个），给 Cursor、Claude Desktop、WorkBuddy 这类只认提示词的客户端用。
3. 测试钉住：技能和提示词里不许让助手把简历、姓名、电话传给工具；不许出现「假岗」「僵尸岗」「不要投」这类判决词。
4. README 第一屏在「已读不回」演示下面加一句：「在 Claude Code 里装上插件，就是一套完整的本机求职工作流：找岗、查公司、改简历、盯投递，简历不出你的电脑。」

预计一个版本做完，不需要新的服务器能力，也不花我们一分钱 token。
