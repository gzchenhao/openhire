# 042 · apply_channel 域名信任校验

日期：2026-09-20 ｜ 测试：355 passed

## 背景：一条别人的推文引出的自查

在 X 上做每日一轮时读到 `@agtnames` 讲「MCP server 返回的第三方文本必须当数据、不能当指令」，
回头查我们自己，发现**我们对第三方文本没有任何处理**。

查完之后风险比我最初说的小得多，但**有一处是真的**。

## 风险面实测（2026-09-20，16,261 条在架）

| 检查 | 结果 |
|---|---|
| 标题/地点里含可疑指令文字 | **0 条**（初筛 52 条全是误报，「Executive **Assistant**」撞了关键词） |
| 返回给 agent 的雇主自由文本 | 只有 `title`、`location`、公司名。**不返回岗位描述** —— 而描述才是注入最常见的藏身处 |
| `apply_channel` 域名 | 全部落在 **18 个**已知 ATS 域名内 |

**结论：原理上的口子存在，今天没有一条在利用它，而且我们的暴露面比多数 MCP server 小。**

## 但有一处必须修

**`apply_channel` 是唯一一个「第三方文本变成对用户机器的动作」的字段。**
`ohp apply` 会把它交给 `webbrowser.open`，而这个字符串来自雇主 ATS 的响应。

`resolve_apply_channel()` 只约束我们**构造**出来的 URL，
**不复查已经存进库的行，也不管某个 vendor 明天会返回什么。**

## 处理

新增 `ats.base.apply_url_is_trusted(url)`，在两个真正要紧的地方生效：

1. **payload**：域名不认识 → `apply_channel` 置空，另给 `apply_channel_blocked`（原文）
   与 `apply_channel_note`（说明 + 建议去公司官网）。
   **不静默丢弃** —— 丢了会让调用方既投不了也不知道为什么。
2. **`ohp apply`**：域名不认识 → **不自动打开浏览器**，打印链接原文 + `ERR_UNTRUSTED_APPLY_URL`
   + 一句「更稳妥的做法是去公司官网招聘页找同一个岗位」。

### 匹配刻意写严

后缀匹配会放过 `evil-zhiye.com`，子串匹配会放过 `zhiye.com.attacker.net`。
两种形态都写进了测试，另外还钉死：纯 http、已知域名只出现在 query 里、`javascript:` 伪协议。

```
在架 16,261 条；未通过信任检查的：0
```

**从来没有任何一条失败过。这个检查存在的意义，是等到第一条失败的那天，它是关着的而不是开着的。**
