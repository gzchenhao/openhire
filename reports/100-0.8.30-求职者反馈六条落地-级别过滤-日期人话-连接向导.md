## 二、级别（第 2 条）

**规则**（`seniority_from_title`，只读标题，不花钱、不改快照，读取时计算）：

- 值：intern、junior、senior、staff、lead、manager、director、unknown；别名 `ic`（intern、junior、senior、staff、unknown：不带人的，包括标题没写级别的）和 `management`（lead、manager、director）。
- 顺序：实习最先；团队负责人 / 组长 / Tech Lead 是 lead（但 Tech Lead Manager 是 manager）；首席科学家、首席架构师、Chief Scientist 是顶级个人贡献者（staff），不是高管；director / VP / Chief / Head / 总监 / 总经理 / 负责人 是 director；manager 和 研发 / 技术 / 工程 / 团队 / 部门经理 是 manager；lead / leader / 主管 是 lead（「工程师/主管」这种带职级选项的岗位不算）；staff / principal / distinguished / architect / 架构师 是 staff；senior / 高级 / 资深 / 专家 是 senior；junior / associate / graduate / 校招 / 应届 / 助理 是 junior。
- 产品经理、项目经理、客户经理、Technical Program Manager 这类「管事不管人」的 manager 先从标题里去掉再判：Senior Product Manager 是 senior，Product Manager 是 unknown，永远不是 manager。中文「经理」单独不算信号（销售经理是销售）。
- 标题没写级别就是 unknown，不猜。

**10-26 快照在架 20,196 条的分布：** unknown 47.5%、senior 19.6%、staff 12.3%、manager 8.7%、director 4.5%、lead 3.8%、intern 1.9%、junior 1.7%。

**赵的场景回放（Zoox，title=perception）：**

- 不带级别，前五条：Senior Manager, Perception Data（35 天）、Data Scientist、Sensing and Perception System Safety Engineer、Senior ML Engineer（103 天）、Director, Perception（366 天）。这就是他看到的。
- `seniority=["ic"]`：Data Scientist、System Safety Engineer、Senior ML Engineer、Principal Software Engineer（191 天）、Senior ML Engineer（526 天）。经理和总监都不在。
- `seniority=["management"]`：Senior Manager, Perception Data、Director, Perception、Senior Manager, Perception、Software Engineering Manager。

排序函数一个字没动（`tests/test_seniority.py::test_ranking_signature_untouched`）：级别是硬过滤，不是排序输入。表格测试 60 个真实标题。

## 三、日期人话与投递前确认（第 3、6 条）

每条岗位现在带：

- `date_source`：employer_ats | employer_self_reported | index_first_seen（比 date_signal 直白，旧字段保留）。
- `dates_in_words`：
  - 理想汽车一条：「雇主系统没有提供发布日期；本工具首次发现日期 2026-10-26，在架至少 2 天；最近核验 2026-10-26，雇主系统当天仍返回这条岗位。」
  - Zoox 一条 103 天的：「雇主发布日期 2026-07-17，在架 103 天；最近核验 2026-10-26，雇主系统当天仍返回这条岗位。在架较久，投递前建议先确认仍在招。」
  - 从不出现「假岗」「僵尸」「不招了」，测试钉住。
- `check_before_apply`：每项一个 code 加中英文，只从量到的事实生成：no_employer_date、self_reported_date、open_over_90d、salary_not_stated、remote_scope_unknown、apply_link_unrecognised、employer_says_closed、date_is_requisition_created。空列表的意思是「这条没有特别要提醒的」，不是「核过了」。10-26 快照 46% 的在架岗位没写薪资，所以 salary_not_stated 会很常见，这是事实。

服务器指令和提示词改成：第一轮最多 5 条，固定六栏（岗位、公司与地点、薪资、为什么匹配、投递前确认、投递链接），日期用 dates_in_words 原句，然后问要不要更多。

## 四、索引状态（第 4 条）

- 原来：工具最多等 180 秒下载，等不到就按空索引回答「本机没有索引，跑 ohp bootstrap」。错在两处：它正在下载；一分钟后就好。
- 现在：下载中 `search_jobs`、`get_company_info`、`check_watches`、`authorize_application` 返回 `index_status: "preparing"`、已等秒数和一句话（「正在准备岗位数据，过一分钟再试」）；`check_watches` 这时不动已通知标记，否则整份快照以后永远不会被当成「新岗」报出来；`watch_intent` 照样保存并标 preparing。下载失败：`index_status: "unavailable"` 加原来的出路。
- 空结果五种开头（`status` + `headline`）：index_empty（本机还没有岗位数据）、known_not_indexed（岗位在读不到的门户上）、unknown_company（索引里没有这家）、unknown_tag（条件里有认不出的词）、no_match（条件都认得，放宽一项）。
- 顺手修的一个隐患：下载期间（180 秒之后）登记的盯岗写在旧文件里，换文件时会丢。现在装快照时把 watches / applications 搬过去（`preserve_user_state=True`），测试覆盖。
- 他说的「环境兼容问题」没有原文，仍等他回复。

## 五、盯岗说明（第 5 条）

- `watch_intent` 返回 `matching_now`（当前匹配条数；盯招聘页的雷达为 null）和 `what_happens_next`：「已保存条件，现在匹配 7 条，都是已有岗位，不是新发。OpenHire 不会主动推送；下次对我说『检查一下』，我只列新出现的岗位（第一次检查会把现在这些先列一遍作为基线）。要定时提醒，在助手里另设定时任务，到点跑 radar_check。」
- `check_watches` 首次拉取：「首次检查：当前匹配 7 条（列出 7 条），都是已有岗位，不是新发；以后只报新增。」第二次：「没有新岗位。」服务器指令和 radar_check 提示词都要求先把这句原样说出来。
- 主动推送不做（stdio 没有服务端推送）。
