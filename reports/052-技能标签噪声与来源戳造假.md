# 052 · 顺着「还有无其他缺陷」查出来的两条数据层缺陷（2026-09-23）

> 领导问：十条修完了吗，还有没有别的。逐条核对时，顺着体验官提的一句「Fleet Technician 标了 scala」往下挖。

## 一、词表正则没加词边界

`src/openhire/pipeline/extract.py` 里的共享技能词表，注释写着「word-boundary matched」，但 `rust`、`scala`、`react`、`transformer` 这些模式是裸字符串。`trust` 里有 rust，`scalable` 里有 scala。

实测（本机库，2026-09-23 在架行）：

| 标签 | 在架行数 | JD 里根本没有这个词的 | 占比 |
|---|---|---|---|
| rust | 2,930 | **2,432** | 83% |
| scala | 2,214 | **1,923** | 87% |

「Senior Account Executive」「Product Manager, Internal Financial Data」「Lead Salesforce Engineer」都标着 rust。**搜 rust 会捞出销售岗。** 这直接伤搜索质量，也伤 044 号报告里「技能词表」那批结论的可信度。

## 二、来源戳记的是「问了谁」，不是「谁答的」

比这更要紧。这些噪声行的来源戳是 `deepseek` / `glm`，但技能列表的顺序和词表字典顺序一模一样（python、rust、java、c++、scala、sql、k8s、aws），是启发式抽取的签名。逐行比对：**3,098 条在架行（deepseek 2,596 + glm 502，占 19%）的技能列表和启发式输出完全相等，却盖着 LLM 的章。**

链路：
1. 每个 LLM 抽取器在 API 报错、JSON 解析失败时**静默退回启发式**（`return self._fallback.extract(job)`）；
2. `ingest._update_job` 在内容变化时用**当前**抽取器（每周 CI 里就是启发式）覆盖 `skills`，**但不动 `extraction_source`**；
3. 月度精抽只挑「不属任何 LLM 源」的行，于是这 3,098 条**永远不会被重新精抽**。

这违反 CLAUDE.md 里的「血统不造假」，而且是我们自己写的机制在造假。

## 三、修了什么（v0.6.4，当天发）

- 词表编译时统一加边界（`_bounded`）：前置 `(?<![a-z0-9])`，后置 `(?![a-z0-9])`；以 `+` 结尾的模式（`c\+\+`）不加后置，`C++17` 仍能命中。`transformer` → `transformers?`，`security engineer` → `security engineer(?:ing)?`。
- `ExtractionResult.extractor`：**由产出结果的那个抽取器签名**（启发式签 `heuristic`，LLM 成功才签自己的名）；`ingest` 插入和更新都照签盖章。
- `scripts/clean_skill_noise.py` 修存量：技能列表等于旧启发式输出的行 → 用修好的启发式重打标签并盖 `heuristic`（下次月度精抽会把它们捡回来）；其余行删掉没有文本依据的词表标签，LLM 自己给的非词表标签不动。
- 测试：`tests/test_skill_noise.py` 钉死 trust≠rust、scalable≠scala、C++17 仍命中、退回启发式的结果必须签 heuristic、更新时来源戳跟着技能走。398 tests。
- 发版：PyPI 0.6.4 · tag · Release 含 mcpb（依赖钉 0.6.4）。
