# 083 · 红线是什么、比越线更好的冷启动、GitHub 生态统筹（2026-10-20）

## 背景

领导 10-20 三问：
1. 「每条岗位的链接，我建议不做」里说的红线是什么？领导的想法：内容是吸引求职者的冷启动钩子，越齐全越好；求职者来了会吸引雇主，雇主和求职者再在 OpenHire 上自己更新数据，内容才能做大。有没有更多冷启动的好办法。
2. 截图里 GitHub 上别人仓库的评论处理过没有；GitHub 所有评论、关注和之后的互动全部归云端统筹，做不了的安排本机会话做。
3. 「私库」指什么，怎么找到本机任务书。

## 一、红线是什么

2026-09 定档，出处 `reports/014`、`reports/020`，2026-09-24 补一条，原文在 CLAUDE.md「抓取边界判例」：

- **请求签名、验证码、登录墙是访问控制，不破。** 响应体里自带密钥的传输编码可以解（Moka 那种），但要客户端算签名的接口不碰。
- **被拦就停，不做特征探测。** 不换 User-Agent、不换 TLS 指纹、不换 IP、不借别人的 cookie 去试。

飞书招聘的岗位列表接口要客户端算 `_signature`，页面还加载验证码组件，所以 2026-09 判为读不了。「在我们这边执行飞书的签名脚本批量读列表」，就是用自动化浏览器替我们算签名，本质上是绕过访问控制。

为什么守这条线，三个理由：

1. **法律风险是刑事级。** 在内地，绕过网站的技术防护措施批量获取数据，有按「非法获取计算机信息系统数据罪」判刑的先例；北京海淀法院审过一起抓今日头条数据的案子，那家公司绕过了字节跳动的反爬措施，单位和直接责任人都被定罪。飞书也是字节跳动的。OpenHire 的运营者是领导本人，这个风险落在个人身上。律师 12 月过目时可以一并确认。
2. **和要拉的雇主正面对立。** 飞书门户上的公司正是我们想请进来自己更新数据的雇主。先绕过他们的防护抓他们的数据，再请他们来，开场就站在了对面；OpenHire 对雇主的承诺「只读、经授权、随时可撤」也就不成立了。
3. **技术上抓不稳。** 签名算法飞书随时能换，今天抓到明天断；被识别后还可能连累我们对其他系统的正常读取。

建议红线不动。领导要改，需要专门裁定，最好等 12 月律师意见。

## 二、比越线更好的冷启动办法

领导的飞轮判断是对的：求职者先来，雇主跟着来，再到双方自己维护数据。分歧只在「求职者这一侧的钩子用什么做」。下面这些不越线，有的比越线拿到的还全：

1. **领导的猎头人脉，是最快的全垒打。** 飞书门户上的 18 家（智元、Momenta、小马、MiniMax、智谱、商汤……）正是 deep tech 猎头最熟的公司。请对方 HR 在飞书开放平台勾两个只读权限（只看已发布岗位，不碰候选人和简历），岗位就完整、合法、带日期地进来，比批量抓到的还全。话术、五步操作图、员工端导出脚本都在（私库 `feishu-employer-optin-template.md`、`feishu-hr-guide.md`，仓库 `scripts/feishu_export.py`），名单今天已更新到 18 家。第一家点头，我当天接上同步；拿下一家，就是对其余 17 家最有说服力的案例。
2. **一个合作打开整个飞书。** 更长线的一步：找飞书招聘团队谈，让他们的官网模板输出标准的 JobPosting 结构化数据（Google for Jobs 用的那种格式），对他们的客户也有好处（岗位能被搜索引擎和 AI 助手读到）。领导在字节跳动有人脉的话值得试。
3. **公众号公告补岗位级链接。** 雇主自己发的公众号招聘文章是一手公开来源，只放链接合法。Xbotics 的 471 条清单在问许可（任务书已交本机）。
4. **求职者自己的助手替他看。** 有浏览器的助手打开飞书门户读给用户听，是用户本人在看，我们不收集；0.8.14 已经让助手主动提出来。
5. **可读系统继续扩。** 31 家门户正在核实，用 Moka、北森、Greenhouse、Workday 等的直接进索引。
6. **钩子不只靠齐全，还靠独家。** 平台给不了的一手数据本身就是钩子：原始发布日、在架天数、近 30 天新发、盯岗提醒。知乎上 BOSS 直聘那条回答到了 7,500 阅读，靠的就是这类数据。建议每周一张「本周新发」表配一篇文章。

建议顺序：求职者侧用「独家数据 + 门户目录 + 盯岗」先拉人；雇主侧由领导用人脉拿下三到五家飞书大厂的授权做样板；有了样板再推「雇主自己更新」。
