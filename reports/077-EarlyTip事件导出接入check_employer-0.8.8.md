# 077 · EarlyTip 事件导出接入 `check_employer`（v0.8.8，2026-10-14）

## 背景

EarlyTip（earlytip.com，一个公开的组织变化与融资并购事件索引）在 2026-10-14 上线了累积事件导出的首版：公开地址 `https://earlytip.com/data/org_events.json`，`schema_version=1`，生产侧声明 83 条，覆盖 2026-09-20 至 10-13 的高管离任、组织调整、融资、并购、破产、新设公司等事件，全部是回填条目（`backfilled=true`），日常追加尚未启用。生产侧同日通知 OpenHire 可以开始读取。

OpenHire 只是这份导出的消费侧：字段（18 个）、事件类型枚举（10 个）、`company_key` 的公开算法、撤回与改名的规矩都由生产侧的规格文件定（决策记录到 D17）。OpenHire 对规格的要求一律写成裁定条目经领导转达，不直接指挥生产侧（10-12 定的分工）。

10-12 的消费侧预案写了四件事：每天最多读一次、过滤撤回；只显示事件类型、日期、来源域名、链接；一张不放链接的域名清单；展示时如实标注来源性质。预案把接入时间放在 2026 年 12 月下旬（导出满 90 天）并要求接入前请律师过一遍域名清单。这次提前接入，理由在第六节；律师过目仍是待办。

## 一、读法（规格 D8）

- `check_employer` 多一项 `org_events`。读取方式是在求职者自己的机器上用一次普通 GET 把整份公开文件拉下来，缓存到 `OPENHIRE_HOME/earlytip/org_events.json`，24 小时内不再下载；比对在本机做。EarlyTip 的服务器只看到一次普通下载，看不到求职者在查哪家公司，更看不到求职者是谁。
- 只认 `schema_version = 1`。别的版本整份拒收（字段含义可能已变），项报 `unavailable` + `reason: schema_version`，提示升级 OpenHire；这种文件不进缓存。
- 网络不通报 `unavailable` + `reason: network`，措辞和 RDAP 那项一样：说的是这次查询的网络，不是雇主。文件读到了但没有这家公司的条目，报 `unavailable` + `reason: no_record`，和包里「来源答了但没记录」的既有语义一致；没有条目不说明任何事，注释里写明。
- 云端容器连不上 earlytip.com（代理 403），和 RDAP、档案馆一样，这项在云端一律 `network`，要本机跑。

## 二、匹配

- `company_key` 按规格二.1 原样复刻：NFKC 再 casefold；按空白和标点切词后从末尾反复去掉 inc / incorporated / ltd / limited / llc / corp / corporation / co / gmbh / ag / plc / sa；删掉全部 Z*、P*、S*、Cc 类字符；中文后缀从末尾反复去掉，每次先匹配最长的（股份有限公司、有限责任公司、有限公司、集团、公司）；结果为空就没有键。测试钉了 13 个例子（`Dulo, Inc.` → `dulo`，`Agile Robots AG` → `agilerobots`，`小米集团有限公司` → `小米`，全角 `ＴｕＳｉｍｐｌｅ` → `tusimple`，`公司` → 空）。
- 雇主这边拿去算键的写法：索引里的双语显示名、它的拉丁半边、它的中文半边，加上「已知未收录」登记表里的别名。键命中条目的 `company_key` 或 `company_aliases` 算作事件主体（`role: subject`），命中 `related_companies` 算作事件另一方（`role: counterparty`，比如被收购方、高管加入的公司）。
- `event_id` 的算法（规范化 url 与标题的 sha256 前 16 位）也复刻了，只用于维护者审计，读取时不重算。

## 三、展示规矩（消费侧自己的，不要求生产侧改）

| 规矩 | 实现 |
|---|---|
| 只给事件类型、一个日期、来源域名、普通链接 | `event_type`、`date`（有 `event_date` 用它，否则用 EarlyTip 的发布日，`date_kind` 标明是哪个）、`source`、`url` |
| 不转标题、不转推荐理由、不转金额 | 返回结构里没有这三个字段；测试断言标题文字不出现在结果里 |
| 站方条款把「链接」本身列为禁止行为的，不放链接 | `url: null` + `link_withheld` 说明；清单六个域名含全部子域：cs.com.cn、bloomberg.com、reuters.com、sina.com.cn、chinastarmarket.cn、cls.cn。生产侧通知只列了前三个，后三个是 10-12 条款核查（新浪协议 8.4、财联社协议 8.2.3）的结论，是 OpenHire 自己的规矩 |
| 撤回的条目不显示 | `retracted: true` 直接过滤，不删不改（D7 的读者侧） |
| 生产侧没能给出公司名的条目跳过 | `company` 为空不参加匹配（D13） |
| 待核实原样带出 | `unverified` 透传，note 里标「（待核实）」 |
| 如实标注来源性质 | 每条 note 结尾固定一句：据 EarlyTip 整理，公司名、金额、日期只与 EarlyTip 自己发布的标题和推荐理由核对过，没有和来源正文逐字核对；这里只转事件类型、日期、来源域名和链接，不转标题 |
| 不刷屏 | 最多 20 条进 `events`，`total` 报全部条数，最新在前 |

MCP 工具说明里加了对应一段，要求助手把事件转述成「EarlyTip 有记录，见来源」，不当成已证实的事实；`no_record` 要说成「文件里没有这家」，不说成「没问题」。

## 四、维护者审计 `ohp org-events-audit`

读者能从文件本身查的项，一条命令跑完（`--file` 审本地副本，`--fresh` 跳过当天缓存，`--json` 给本机任务队列用）：

- 结构：每条 18 个键齐全；没有 `why` / `critic` / `cat`；`event_count` 等于条数。
- 重算：`event_id` 按规范化 url + 标题重算一致且全局唯一；`company_key` 按公开算法重算一致；`source` 等于 url 主机名去 www.。
- 规矩：`company` 不含括号；日期格式 `YYYY-MM-DD`；`published_date` 不落在 2026-09-29 至 10-03；`unverified: true` 的标题必须带「待核实」（反向允许，待核实转实后标题保留原样是规格三.3）；融资类 `related_companies` 必须为空（D10）；`retracted` 必须带 `retracted_at`。
- 覆盖率（不算问题）：`amount` 与 `event_date` 在标题里出现的比例。D3 说的是出现在标题或推荐理由里，推荐理由不导出，所以只能对标题查，报比例不报失败。
- 统计：事件类型分布、来源域名分布、不放链接的域名命中数、发布日期范围、公司名全表、同一键对应两个公司名的冲突（规格六.d）。

`problem_count` 不含 `company_null`（规格允许）和 `*_not_in_title`（只能对标题查）。

本机任务队列的 `ALLOWED` 加了这个子命令（它只读、只下载公开文件）。**首版的真实审计已排进队列**（`org-events-audit --fresh`，加三条 `check-company`：理想汽车、Boston Dynamics、高通，看匹配是否命中），本机跑完结果回传后再决定要不要出新的裁定条目。若 `event_id_mismatch` 是全体不一致，那是我这边规范化细节（比如去掉「待核实」后要不要再去首尾空白）与生产侧实现的差异，改读者侧，不是生产侧的问题。

## 六、为什么提前接入，以及待领导定的事

10-12 的预案把接入放在导出满 90 天之后，图的是生产侧的日常追加流程先跑出一段记录。现在的情况是：生产侧按它的验收流程上线了首版并通知可读；首版是静态回填（日常追加未启用，文件固定 83 条），不存在「追加过程出错」这一层风险；读者侧能做的全部保护（只转类型 / 日期 / 域名 / 链接、六个域名不放链接、撤回过滤、出处声明）都已写进代码和测试，法律暴露面只剩「普通跳转链接」这一项，而这项在 10-12 的条款核查里已经按最保守的口径处理。等 90 天只会让求职者晚两个月看到一个有用的事实项，所以提前。

待领导定：
1. **律师过目域名清单**（预案里的接入前步骤，现在是接入后补做）：一小时的事，做不做、什么时候做。
2. **要不要把 `amount` 也展示**：它是 D3 校验过的原样金额，对融资类事件有用；这次按 10-12「只显示四样」的裁定没放，放开是一行改动。
3. 本机跑一次任务队列（先 `git pull` 并重装包，新子命令在 0.8.8 里）：`.venv\Scripts\python.exe scripts\run_local_tasks.py --sync`。

下一步：等审计结果出裁定条目；日常追加启用后次日再跑一次审计，核对旧 `event_id` 全在、总数等于旧数加新增（规格六.f 的读者侧）。

## 七、发版后记（10-14 05:10 UTC 自检）

PyPI、Release、mcpb 都正常。Registry 工作流红了三次，真因是**列表接口每页 30 条、最旧在前，0.8.8 是这个服务器的第 31 个版本**：核对步骤只读第一页，看到的是 0.1.1 到 0.8.7 且没有任何 isLatest，于是把一次成功的发布判成失败；重跑则被 Registry 以「duplicate version」拒绝，恰好证明已发布。核对改成 `scripts/registry_state.py`：`limit=100` 并跟 `metadata.nextCursor` 翻页，退出码分开「已标 latest / 在库里没翻标 / 不在 / 读不到」，在库里就算发布成功，只有「答了且不在」才红；Publish 一步把 duplicate 当已发布。验证运行 38515084510 绿：`versions=31 newest=0.8.8 latest=0.8.8`。另：`/v0/servers?search=` 接口当天对 runner 常 20 秒超时，而 validate 与 publish 秒回，脚本 curl 优先、urllib 兜底。
