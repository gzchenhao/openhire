| # | 体验官结论 | 核验结果 |
|---|---|---|

### ① 的真相与处理

两个调用点都是：
```python
anchor = _aware(job.posted_at) if job.posted_at else _aware(job.first_seen_at)
```
锚点确实是雇主自己的发布日。**但函数签名写的是 `compute_ghost_score(relist_count, first_seen_at, now)`** ——
这是第一版的真相，加入 posted_at 之后就一直在说谎。

**为什么这条必须修，哪怕它没改变任何数字**：这个参数名出现在雇主最可能质疑我们的那个函数上，
而它指向的正是我们最怕被指控的事（「你们拿自己的抓取日给我们打分」）。
读代码的人分不清「过时的名字」和「真的 bug」，本例中过时的名字读起来正好就是最坏的那个 bug。

处理：改名 `age_anchor`（原语 `days_open`），补文档说明它到底装什么，
新增测试把**签名与两个调用点钉死**，防止名字再次漂走。

## 二、顺带修正的数字

README 与 MCP docstring 里「ghost≥0.99 中近 30 天被动过」的比例：**67% → 75%**，标注实测日期。
原因：CI 刷到了本机连不上的北森租户，本次是**当天数据**。

该数字的三个版本：36%（口径错误，已公开发布过）→ 67%（口径正确、数据 13 天旧）→ **75%（当天）**。
三次修正**方向一致**，说明 `ghost_score` 对雇主是系统性偏严的。

## 三、E1 / E2 / E3 已做（领导批准）

**E1 · 被点名后的第一小时是空的**
README 第一屏加入中英双语入口块：说明这个数字是什么、认领链接、
并在同一句里给出「也可以直接要求移除」。原来雇主要读到第五节才看得到认领入口。

**E2 · 认领流程在中文 HR 语境走不通**
- 新增完整中文 issue 模板 `employer_claim_zh.yml`
- 两个模板同时加入三条承诺：**3 个工作日内答复** / **认领不带来任何付费后续** / **身份材料只核验不留存**
- 明确「可由任何人代为提交，我们核验的是**企业**身份，不是提交人的账号」

为什么这条优先级最高：**用北森的公司恰恰是我们数据最弱的一批**（拿不到 `updated_at`，
永远只能显示「—」），而它们的 HR 恰恰最不可能有 GitHub 账号。

**E3 ·「幽灵」在雇主页面上没有被管理**
- `get_company_info` 新增三个伴随字段，让分数自带限制条件：
  `median_days_open` / `relisted_postings` / `last_touched_reported_by_ats`
- 实测对比：

| | ghost_avg | median_days | relisted | last_touched 可得 |
|---|---|---|---|---|
| 宇树科技 | 0.7024 | 368 | **0** | **false** |
| Elastic | 0.0996 | 27 | 20 | true |

同一个字段，读者能立刻看出两家的分数不是一回事。
- 对外文案去掉「ghost jobs scored / 幽灵岗位打分」，改为实际测量的东西。

## 四、E4 / E5 的处置

- **E4（认领后雇主看不到生效）**：承认有价值，但**当前零认领**，做了没人看。等出现第一个认领再做。
- **E5（主动告知被收录雇主）**：**领导决定：被动等对方发现。** 主动通知会主动招来质疑，
  也可能招来大量移除请求，属于产品定位决策而非工程问题。

## 五、对「回复宇树老板模板」的修改意见

体验官给的 300 字模板写得好，但有两处会翻车：
1. 「贵司那几个 1.0 分」—— 现在是 **22 条**不是 37 条
2. 「45 天合理窗口」—— 这是在告诉对方我们的阈值是拍脑袋定的，他会追问「凭什么 45 天」，我们答不上来

建议把第 2 点反过来用：**主动说「45 天是我们自己设的经验阈值，没有行业依据，
所以 1.0 分从来不是结论，只是值得问一句」** —— 自己先掀开最弱的地方，比等对方掀开好。
