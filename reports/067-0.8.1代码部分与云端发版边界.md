## 二、云端会话推不了 tag（边界，不是故障）

`git push origin v0.8.1` 五次都是 HTTP 403（`RPC failed; HTTP 403`），分支推送同一秒是成功的。改走 GitHub REST API 建 tag（`gh api repos/gzchenhao/openhire/git/tags`），代理直接回：

```
Write access to this GitHub API path is not permitted through this proxy. (HTTP 403)
```

结论：云端会话的 git 代理只放行**分支**推送，tag 的建立（git 协议或 API）都不许。代理文档写明 403 是策略拒绝，要上报不要绕，所以我停在这里。`mcp__github__*` 工具集里也没有建 tag / 建 Release 的工具。

**tag 由领导在本机推，一条命令（在 `C:\openhire` 里；这一步不碰 venv，不用先停 Claude Desktop 里的 openhire）：**

```
git fetch origin main && git tag -a v0.8.1 -m v0.8.1 5bd4298 && git push origin v0.8.1
```

本机 main 若落后于远端，先 `git checkout main && git pull --ff-only origin main` 再打 tag。

## 四、发版剩下三步（按顺序）

1. **领导本机推 tag**（第二节那条命令）。
2. **Actions → Release → Run workflow，填 `v0.8.1`**：PyPI 可信发布 + mcpb 打包 + GitHub Release 一次走完，不再 twine。这是 `release.yml` 第一次跑；成功后下一次改成推 tag 自动触发，并让 Registry 排在它后面（`release.yml` 顶部注释已写明）。我没有擅自触发：发 PyPI 不可撤回，领导说一声我就跑。
3. tag 一推，「Publish to MCP Registry」工作流会被 `v*` tag 自动触发；Registry 校验 PyPI，那时 0.8.1 还没上 PyPI，这次自动跑**预期失败**（领导会收到 GitHub 的失败邮件，不用理）。第 2 步成功后到 Actions 里对它 **Re-run** 一次，看到 `server.json=0.8.1 registry-isLatest=0.8.1` 即可。
4. 发完按「有事才发」在 X 发一条（本机会话，走 Web Intent）。
