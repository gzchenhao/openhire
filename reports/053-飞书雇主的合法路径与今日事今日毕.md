## 三、飞书：五条路都走了一遍，结论有证据

工作流 7 个 agent、257 次工具调用，只做普通 GET（Chrome UA，无 cookie，无签名，无登录），12 个租户逐一复核，原始响应存档在 scratchpad。

**飞书招聘官网本身：没有任何不签名就能拿到职位数据的路径。** 详情页 200、170 KB，但服务端只渲染 `<title>`（职位名 + 官网名），正文 9 个字符，无 og 标签、无内嵌 JSON、无 robots、无 sitemap、无 RSS。列表接口不签名回的是一个 HTML 壳。**判 CLOSED，按 020 判例不碰。**

**飞书开放平台官方接口有，但只认雇主自己的 tenant_access_token**（`hire:site_job_post:readonly`，返回标题、JD、城市、部门、创建时间、在架状态，字段比 Greenhouse 还全）。这是雇主授权之路，和「雇主认领」完全对齐。

**真正的突破口是雇主自己在别处公开的第一方镜像**（验证员复核通过，普通 GET，无访问控制）：

| 雇主 | 第一方来源 | 字段 | 发布日期 |
|---|---|---|---|
| **蔚来** | `www.nio.cn/careers/jobs` 的 `__NEXT_DATA__` | **1,784 条社招**，id 就是飞书 id，投递链接指飞书详情页 | **有**（`open_date` 精确到秒） |
| **理想** | `api-web.lixiang.com` 自建后端 | 772 条社招 + 校招，**完整 JD** | 无 |
| **银河通用**（社招） | Moka `yinhetongyong/165929`，明文 init-data | 123 条 | 有 |
| **月之暗面** | Moka `moonshot/148506` | 106 条 | 有 |
| 阶跃星辰 | Moka `step/94904`（验证员未复核） | 待验 | 待验 |

**7 家优先公司的判定：** 蔚来 open（列表级，缺 JD）· 理想 open（缺日期）· 银河通用 open（社招）· 地平线 **不在飞书**（Wintalent/hotjob 托管，海外用 Lever）· Momenta / 小马智行 / 智元 **closed**，只剩雇主授权一条路。

**一个探查报的警报是假的：** 探查说 `app.mokahr.com` 现在对首次 GET 一律 302 + Set-Cookie，怀疑现有 13 个 Moka 租户在悄悄变陈旧。查了今天 11:56 的刷新日志：元戎 92、MINIEYE 40、速腾 161、驭势 52、福瑞泰克 74、白犀牛 33、主线 45，全部 ✓。我们的 httpx 客户端本来就跟随重定向并带 cookie jar，不需要修。

**明确不做的：** 用搜索引擎发现的 URL + `<title>` 建「只有标题」的行。没有日期、没有 JD、没有城市的记录，ghost_score 每个输入都是零，排到哪里都是在假装知道。也不用 LinkedIn 游客接口和猎聘（技术上能拿到日期，但不是雇主第一方，与定位不符）。

## 四、正在做（当天开工）

三个实现 agent 各在自己的 worktree 里，一个反驳型审查者盯每条分支：

1. **蔚来第一方适配器**：一次 GET，解析 `__NEXT_DATA__`，`open_date` 直接喂 `days_open`，`description_raw` 留空，**空描述不许跑出任何技能标签**（这是今天刚踩过的坑）。
2. **理想第一方适配器**：列表 + 详情，完整 JD 可以抽技能；`posted_at=None` 走首见回退，`ghost_reason` 要说清「雇主镜像不带发布日期」。
3. **「已知未收录」登记表**：Momenta、小马、智元等 10 家，`search_jobs` 和 `get_company_info` 不再回「没收录」四个字，而是回门户 URL、原因（列表接口要求请求签名，我们视为访问控制，不绕）、以及雇主能授权的两个只读 scope。小马那位工程师至少知道为什么缺、去哪里看。

外加：三个 Moka 租户用我们自己的适配器验证后加进 seed，触发一次快照刷新。

robots 已查：`nio.cn` 只禁 /admin、/node、/account 等，不涉 careers；`lixiang.com` 禁带 query 的 URL，但 API 在另一个 host（无 robots），详情页无 query。
