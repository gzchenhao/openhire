## 一、装机文案：五个助手都点名，每个都给能走通的路

改了 README 的主句（「turns any MCP-speaking assistant」那段）、Quickstart 的「New to MCP」提示块、Works with 里新增豆包与 DeepSeek 两节，以及 `docs/employers.html` 雇主页的那句「候选人把它装进 … AI 助手」。规矩写进 CLAUDE.md 对外文案第 7 条，往后知乎、LinkedIn、目录描述一律照此。

写法上有两处必须准确，不能为了代入感写出一条走不通的路：

- **豆包（豆包工作）**：它的「技能·连接器·伙伴 → 新建自定义连接器」只收 HTTP 地址，不收命令行。所以给它的路径是本机先 `ohp serve --transport streamable-http --port 8000`，再把 `http://127.0.0.1:8000/mcp` 填进自定义连接器。索引、指纹和匹配仍全在用户自己的电脑上，豆包只是通过本机端口调用。**这段按豆包连接器的公开说明写，没有在豆包里实测**，README 里明写了这一句，等领导在豆包工作里试一次再删。
- **DeepSeek**：DeepSeek 自己的 App 没有 MCP 入口。写法是「把 DeepSeek 当模型用在支持 MCP 的客户端里（Cherry Studio、Chatbox、Cline、WorkBuddy、TRAE）」，再给那个客户端填 `uvx` 配置；Cherry Studio 的菜单路径写了。
- WorkBuddy 原来就有一节（`~/.workbuddy/mcp.json`），这次把它提到「贴给你的 agent」那行里。

## 三、飞书：谁都读不了列表接口，能读的只是渲染出来的那一页

事实分三层：

1. **飞书招聘的列表接口要请求签名**（`_signature`），这是访问控制（020 判例）。WorkBuddy 也没有这把钥匙；飞书开放平台的 `hire:site_job_post:readonly` 要雇主自己授权给某个应用，WorkBuddy 不会凭空拿到某家雇主的授权。
2. **带浏览器工具的助手能做的**，是像人一样打开 `xxx.jobs.feishu.cn` 看渲染出来的页面：一次一页、没有发布日期、没有历史、关了页面什么也不剩。这不是「读接口」，是「替人看一眼」。OpenHire 不做无头浏览器渲染是有意的（抓取边界），不是做不到。
3. **OpenHire 的价值不在那一页**：索引里 143 家雇主的发布日期、在架天数、重挂、盯岗、板的现读与消失记录，都是「看一眼」给不了的。两者互补，不冲突。

把互补写进产品，让助手自己接上：`ats/boards.py` 加 `BROWSER_HINT`（「助手有浏览器工具的话，可以直接打开这个门户阅读：现读、不入库、不盯、无发布日期」），接在飞书、Lark、Workday、SuccessFactors、Taleo、iCIMS 六类封闭门户的拒绝理由后面；LinkedIn、JobsDB、BOSS 是招聘网站不是雇主系统，不加。`service.known_not_indexed_hint` 对有门户地址的已知未收录雇主加一句英文同义提示（「an assistant with a browser tool can open that portal and read the listings as a person would; OpenHire does not index, date or watch what that page shows」）。两条测试钉住。

于是 WorkBuddy 问「小马智行在招什么」时，OpenHire 回的是：门户地址、为什么不收录、雇主怎样能让我们收录、以及「你有浏览器就自己打开看」。不尴尬，分工清楚。
